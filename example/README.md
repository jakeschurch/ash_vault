# AshVault example

A small, complete application that demonstrates AshVault end to end: two tenants,
two resources sharing one tenant key, OpenBao-backed key material, Ash policies, and
a `pg_dump` / restore cycle that proves a database backup cannot undo a
crypto-erasure.

Everything here is runnable. `mix example.demo` narrates the whole story in the
terminal, and step 7 is the one that matters.

---

## What it contains

| File | What it shows |
|---|---|
| `lib/example/accounts/organization.ex` | The tenant. It **owns the key scope** (`scope_owner? true`) and therefore carries `key_lifecycle` — the generated `:rotate_key` and `:destroy_keys` generic actions. |
| `lib/example/accounts/user.ex` | `encrypt :email`, plus a **field policy** on the decrypted field. |
| `lib/example/accounts/contact.ex` | `attributes [:phone]` — a *second* resource under the *same* tenant key. |
| `lib/example/vault.ex` | The vault, and the config switch between the OpenBao and Local key providers. |
| `lib/example/backup.ex` | Real `pg_dump` (via `docker exec`) and real `psql` restore. |
| `lib/mix/tasks/example.setup.ex` | Creates the database, migrates it, prepares the key provider. |
| `lib/mix/tasks/example.demo.ex` | The seven-step demonstration. |
| `priv/repo/migrations/` | Generated by `mix ash_postgres.generate_migrations`. Worth reading: there is no `email` column and no `phone` column, only `encrypted_email bytea` and `encrypted_phone bytea`. |

### Why `key_lifecycle` lives on `Organization` and not on `User`

The key scope is `:tenant`. Every encrypted field on every tenant-scoped resource —
`User.email` *and* `Contact.phone` — is encrypted under one key per organization.
"Rotate the key" and "erase the key" are therefore operations on the **organization**,
not on a resource that happens to have an encrypted field. Putting `key_lifecycle` on
`User` would let you write `User.rotate_key`, which is a misdescription: it would also
rotate the contacts, because it is the same key.

AshVault enforces this: `key_lifecycle` requires `scope_owner? true`.

Step 6 of the demo makes it visible — one `destroy_keys` on `Organization` and *both*
resources stop decrypting for that tenant.

### Two subtleties worth knowing

**AAD binding.** One key per tenant does not mean one interchangeable ciphertext.
The cipher binds additional authenticated data that includes the scope, the resource
module and the field name, so a `User.email` envelope pasted into
`contacts.encrypted_phone` fails authentication instead of decrypting. One key,
per-field binding.

**Key versions live in the envelope, not in your head.** The stored value is a
self-describing envelope: magic `AV`, format version, cipher id, **key version**,
nonce, tag, ciphertext. Step 5 of the demo decodes the raw `bytea` with
`AshVault.Envelope.decode/1` rather than inferring the version from "decryption
worked" — which would pass even if `rotate_key` did nothing at all.

## Prerequisites

* Elixir 1.17+ / OTP 26+
* PostgreSQL 16+ reachable on `localhost:5432` as `postgres`/`postgres`
* The PostgreSQL **container** name, because `pg_dump` is not on this host's PATH —
  it lives inside the container. Default `foundrybox-postgres-1`; override with
  `PGCONTAINER`. `psql` *is* needed on the host PATH, for the restore.
* An OpenBao (or Vault) dev server at `http://127.0.0.1:8200` with token
  `ashvault-root`, if you run with the default provider:

  ```sh
  docker run -d --name ashvault-bao -p 8200:8200 \
    -e BAO_DEV_ROOT_TOKEN_ID=ashvault-root \
    openbao/openbao:2.6.2 server -dev -dev-listen-address=0.0.0.0:8200
  ```

  Not needed if you run with `ASHVAULT_PROVIDER=local`.

The example only ever names the database `ash_vault_example`. It does not touch
`foundry_dev` or `ash_vault_test`.

## Setup, in order

```sh
cd example
mix deps.get
mix compile

# create ash_vault_example, run the migrations, prepare the key provider
mix example.setup

# the seven-step walkthrough
mix example.demo
```

To start over from an empty database:

```sh
mix example.setup --reset
mix example.demo
```

The demo mints **fresh organization ids on every run**, deliberately. OpenBao
tombstones are permanent and outlive the database, so a hardcoded tenant id would be
crypto-erased by the first run and every later run would fail at its first write.

## Switching key providers

```sh
ASHVAULT_PROVIDER=openbao mix example.setup && ASHVAULT_PROVIDER=openbao mix example.demo  # default
ASHVAULT_PROVIDER=local   mix example.setup && ASHVAULT_PROVIDER=local   mix example.demo
```

| Provider | Key material | Erasure primitive |
|---|---|---|
| `AshVault.KeyProviders.OpenBao` | An exportable transit key per tenant, versioned 1:1 with AshVault key versions. | `DELETE` the transit key (every version at once) plus a tombstone in a KV-v2 mount. |
| `AshVault.KeyProviders.Local` | `<root>/<scope>/vN.key` files, mode 0600. Root at `ASHVAULT_LOCAL_ROOT`, default `/tmp/ash_vault_example_keys`. | Tombstone **first**, then shred and unlink the key files. |

Both satisfy the property the library is built on — the keys are in a system that is
not the database — but they are not equally strong.

> **`Local` comes with a sharp operational rule.** The key root must be excluded from
> the database backup job, and should not sit on a volume you snapshot with the
> database. If both land in the same tarball, crypto-erasure is defeated and the
> guarantee is void. Back the key root up *separately*, deliberately, with its own
> retention policy — and understand the tradeoff: backups of keys make erasure harder,
> and no backups of keys make total data loss easy. There is no free answer.

`Local` is also single-node. Two nodes over one NFS mount will race; use OpenBao.

Both providers require a one-time operator step, which `mix example.setup` performs:

* `Local`: `init_root!/1` creates the root (mode 0700) and a sentinel file. The
  provider **refuses to start** without that sentinel, so an unmounted key volume
  cannot masquerade as a pristine, never-used key store and quietly mint fresh keys.
* `OpenBao`: `setup/0` mounts the KV-v2 engine that holds tombstones. The provider
  deliberately never creates that mount on a *read*, because a missing mount answers
  `404` — status-identical to "no tombstone here" — and auto-provisioning it would be
  fail-open: a fresh empty mount makes every erased tenant look intact again.

## What each step proves

| Step | Claim |
|---|---|
| 1 | Two tenants, ordinary Ash writes. Nothing about the calling code is encryption-aware. |
| 2 | **Raw SQL sees ciphertext only.** The decoded envelope header is printed, the table has no plaintext column at all, and every `bytea` is scanned for the plaintext needles. |
| 3 | Through Ash the same rows read back as plaintext. `decrypt_by_default` means no explicit `load`. |
| 4 | A field policy denies `User.email` to a non-admin actor — it arrives as `%Ash.ForbiddenField{}`, and the decrypt calculation passes it through instead of decrypting it. A separate action policy refuses `rotate_key` to that actor: key lifecycle is as guarded as you make it. |
| 5 | **Rotation.** `rotate_key` mints v2; new writes carry key version 2 while existing rows still carry 1, decoded from the stored bytes, byte-identical to before. Org B, a different scope, is untouched. |
| 6 | **Crypto-erasure.** One `destroy_keys` on `Organization` and both `User` and `Contact` reads for that tenant return `AshVault.Errors.KeyDestroyed` — never `AuthenticationFailed`, because erasure must not look like tampering. The rows are all still in PostgreSQL. Org B is unaffected. |
| 7 | **The point.** A `pg_dump` taken *before* the erasure is restored into a freshly created database. Every byte of the ciphertext comes back, bit for bit — and it is still undecryptable, because the key was never in the dump. |

Step 6 also asserts the negative on the dump itself: no plaintext in any encoding, and
no raw key material in raw, hex or base64 form — after first asserting the positive
controls, because "no plaintext in the dump" is a worthless claim about a dump that is
empty, schema-only, or of the wrong database.
